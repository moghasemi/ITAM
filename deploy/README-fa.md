# راهنمای نصب، راه‌اندازی و نگهداری ITAM

این راهنما دو سناریو را از هم جدا می‌کند:

1. **دموی محلی روی یک رایانه:** SQLite و دسترسی فقط از همان رایانه.
2. **پایلوت استانی/محیط عملیاتی:** PostgreSQL، اجرای Waitress پشت Reverse Proxy دارای HTTPS، پشتیبان‌گیری قابل‌بازیابی و دسترسی شبکه کنترل‌شده.

SQLite و اجرای مستقیم HTTP برای دموی محلی هستند؛ برای پایلوت استانی PostgreSQL و HTTPS را به‌کار ببرید. معماری برنامه Django و قالب‌های سمت سرور است.

---

## ۱. پیش‌نیازها

| مورد | دموی محلی | پایلوت استانی |
|---|---|---|
| سیستم‌عامل | Windows 10/11 | Windows Server یا میزبان سازمانی پشتیبانی‌شده |
| Python | 3.12، ۶۴ بیتی | 3.12، ۶۴ بیتی |
| پایگاه داده | SQLite | PostgreSQL |
| وب‌سرور برنامه | Waitress | Waitress پشت Reverse Proxy |
| ارتباط | localhost | HTTPS با گواهی معتبر در شبکه سازمان |
| پشتیبان | فایل SQLite و media | pg_dump و media و فایل .env |

برای نصب آفلاین، بسته‌های Python و وابستگی‌ها را از قبل روی رسانه مورد تأیید سازمان آماده کنید. اجرای سامانه برای کاربر نهایی به اینترنت عمومی نیاز ندارد؛ اما به‌روزرسانی بسته‌ها و دریافت گواهی/نصب زیرساخت ممکن است به فرایند جداگانه سازمان نیاز داشته باشد.

## ۲. دریافت و آماده‌سازی پروژه

PowerShell را باز کنید:

```powershell
cd D:\itam
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

فایل تنظیمات محیطی را در ریشه پروژه بسازید. این فایل محرمانه است و نباید در Git ثبت یا برای کاربران عادی ارسال شود.

### دموی محلی

```powershell
Copy-Item deploy\.env.sqlite.example .env
```

در فایل `.env` مقدار `ITAM_SECRET_KEY` را با خروجی دستور زیر جایگزین کنید:

```powershell
.\.venv\Scripts\python.exe -c "import secrets; print(secrets.token_urlsafe(64))"
```

این نمونه فقط برای دسترسی localhost است. `ITAM_SECURE_COOKIES=0` را به شبکه سازمانی یا اینترنت تعمیم ندهید.

### پایلوت استانی

```powershell
Copy-Item deploy\.env.example .env
```

سپس مقادیر واقعی را تنظیم کنید:

- `ITAM_SECRET_KEY`: کلید تصادفی اختصاصی با حداقل ۵۰ نویسه؛ از کلید نمونه استفاده نکنید.
- `ITAM_ALLOWED_HOSTS`: نام DNS واقعی سامانه؛ هرگز از `*` استفاده نکنید.
- `ITAM_CSRF_TRUSTED_ORIGINS`: مبدأ HTTPS واقعی سامانه.
- `ITAM_DB_*`: نام پایگاه، کاربر اختصاصی برنامه، گذرواژه قوی، میزبان و پورت PostgreSQL.
- `ITAM_PUBLIC_BASE_URL`: نشانی HTTPS واقعی که در QR تجهیزات درج می‌شود.

برای PostgreSQL یک پایگاه و کاربر اختصاصی برنامه بسازید؛ برنامه را با کاربر superuser پایگاه داده اجرا نکنید. فایل `.env` را فقط برای حساب سرویس و مدیران مجاز قابل خواندن کنید.

## ۳. آماده‌سازی پایگاه داده و حساب مدیر

### PostgreSQL (پایلوت)

ابتدا PostgreSQL را نصب و پایگاه/کاربر اختصاصی را ایجاد کنید. پیش از Migration روی پایگاه موجود، از آن پشتیبان قابل‌بازیابی تهیه کنید؛ بخش پشتیبان‌گیری را ببینید.

### اجرای Migration و ساخت مدیر اولیه

این دستورات را فقط در زمان نصب اولیه یا به‌روزرسانی برنامه و پس از پشتیبان‌گیری اجرا کنید:

```powershell
.\.venv\Scripts\python.exe manage.py check
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py collectstatic --noinput
.\.venv\Scripts\python.exe manage.py createsuperuser
```

### بارگذاری جغرافیای سازمانی ایران برای پایلوت

پس از Migration و پیش از ایجاد کاربران استانی/مراکز، ساختار استان‌ها و شهرستان‌ها را بارگذاری کنید:

```powershell
.\.venv\Scripts\python.exe manage.py load_iran_geography --dry-run
.\.venv\Scripts\python.exe manage.py load_iran_geography
```

فرمان تکرارپذیر و افزایشی است؛ رکوردهای موجود را حذف نمی‌کند. در پیکربندی اولیه فقط «سیستان و بلوچستان» و شهرستان‌های زیرمجموعه آن فعال می‌شوند و سایر استان‌ها/شهرستان‌ها غیرفعال می‌مانند. پس از اجرا، تعداد ۳۱ استان و ۴۸۴ شهرستان و وضعیت فعال بودن استان هدف را بررسی کنید. این فرمان مرکز عملیاتی، کاربر یا دارایی ایجاد نمی‌کند؛ مراکز واقعی سازمان را بعداً با کد و ساختار مصوب همان استان ثبت کنید. داده منبع برای seed اولیه است و جایگزین فهرست حقوقی/اداری مورد تأیید سازمان نیست.

پس از بارگذاری جغرافیا، حساب‌های واقعی و نقش‌های مصوب را ایجاد کنید و واحد سازمانی/استان هر کاربر را دقیق تعیین کنید. حساب superuser را برای استفاده روزانه کاربران نسازید؛ حساب شخصی و نقش محدود برای هر کاربر ایجاد کنید.

**در محیط واقعی `seed_demo`، گذرواژه نمونه یا حساب‌های آزمایشی را اجرا نکنید.** برای حذف داده‌ها از `flush` استفاده نکنید؛ این دستور تمام داده‌های پایگاه را پاک می‌کند.

## ۴. اجرای محلی برای دمو

برای دموی همان رایانه:

```powershell
.\.venv\Scripts\python.exe manage.py check
.\deploy\run_server.bat
```

نشانی محلی: `http://127.0.0.1:8000/`

اسکریپت فقط Waitress را اجرا می‌کند، روی Loopback گوش می‌دهد و در صورت نبود Waitress متوقف می‌شود. سرور توسعه Django به‌عنوان جایگزین اجرا نمی‌شود. این حالت برای ارائه محلی است و کاربران دیگر رایانه‌ها به آن دسترسی ندارند.

## ۵. اجرای پایلوت در شبکه سازمان

در محیط عملیاتی، Waitress روی `127.0.0.1:8000` اجرا می‌شود و Reverse Proxy باید TLS/HTTPS را خاتمه دهد و درخواست‌ها را به Waitress منتقل کند.

الزامات پیش از بازکردن دسترسی کاربران:

1. گواهی TLS و نام DNS سازمانی آماده باشد.
2. Reverse Proxy هدر `X-Forwarded-Proto: https` را تنظیم کند.
3. نام میزبان در `ITAM_ALLOWED_HOSTS` و مبدأ HTTPS در `ITAM_CSRF_TRUSTED_ORIGINS` ثبت شده باشد.
4. `ITAM_USE_PROXY_SSL_HEADER=1` و `ITAM_SECURE_COOKIES=1` باقی بمانند.
5. فایروال فقط پورت HTTPS پروکسی را از شبکه‌های مجاز بپذیرد؛ پورت 8000 نباید مستقیماً برای شبکه باز شود.
6. پوشه `media` را مستقیماً از وب‌سرور عمومی سرو نکنید؛ دسترسی به پیوست‌ها باید از مسیرهای احراز هویت‌شده برنامه باشد.

پس از آماده‌شدن این موارد، نصب وظایف ویندوز را با PowerShell دارای دسترسی Administrator انجام دهید:

```powershell
cd D:\itam\deploy
.\install_service.ps1 -ProjectPath "D:\itam"
```

اسکریپت، تنظیمات Django را بررسی می‌کند، فایل‌های ایستا را جمع‌آوری و وظیفه اجرای Waitress و وظایف دوره‌ای را ثبت می‌کند. **این اسکریپت Migration اجرا نمی‌کند و پورت برنامه را در فایروال باز نمی‌کند.** Migration باید جداگانه و پس از پشتیبان‌گیری انجام شود.

وظایف دوره‌ای ثبت‌شده:

- `ITAM-SLA` هر ۳۰ دقیقه: بررسی نقض SLA.
- `ITAM-Visits` روزانه ساعت ۰۷:۰۰: علامت‌گذاری بازدیدهای ازدست‌رفته.
- `ITAM-Backup` روزانه ساعت ۲۳:۳۰: پشتیبان‌گیری پایگاه داده و رسانه‌ها.
- `ITAM-Dispatch` هر ۵ دقیقه: پردازش Outbox. تا زمانی که مقصدهای واقعی یکپارچه‌سازی تعریف و تأیید نشده‌اند، مقصد خارجی فعال نکنید.

## ۶. پشتیبان‌گیری و بازیابی

### پشتیبان‌گیری

```powershell
.\deploy\backup.ps1 -ProjectPath "D:\itam" -BackupRoot "\\backup-server\itam" -KeepDays 90
```

اسکریپت با توجه به `ITAM_DB_ENGINE` یکی از این دو روش را به‌کار می‌گیرد:

- SQLite: SQLite Backup API، سازگار با WAL.
- PostgreSQL: ابزار `pg_dump` با قالب custom.

در هر دو حالت پوشه `media` و فایل محرمانه `.env` نیز کپی می‌شوند. دسترسی به محل پشتیبان باید محدود باشد؛ پشتیبان را فقط روی همان دیسک سرور نگه ندارید. پایان موفق اسکریپت به‌تنهایی جایگزین آزمون دوره‌ای بازیابی نیست.

### بازیابی SQLite

1. وظیفه `ITAM-Server` را متوقف کنید.
2. فایل `db.sqlite3` را از مجموعه پشتیبان به مسیر تنظیم‌شده در `ITAM_DB_PATH` برگردانید.
3. پوشه `media` و فایل `.env` متناظر همان پشتیبان را بازیابی کنید.
4. وظیفه سرور را اجرا و ورود و مشاهده چند رکورد و پیوست را آزمایش کنید.

### بازیابی PostgreSQL

1. وظیفه `ITAM-Server` را متوقف کنید.
2. پایگاه مقصد را طبق رویه DBA آماده کنید.
3. فایل `itam-postgresql.dump` را با `pg_restore` بازیابی کنید؛ از مالکیت/نقش‌های مورد تأیید سازمان استفاده کنید.
4. `media` و `.env` همان مجموعه پشتیبان را بازیابی کنید.
5. سرور را راه‌اندازی و ورود، گزارش‌ها، پیوست‌ها و گردش کار را آزمایش کنید.

بازیابی را ابتدا در محیط آزمایشی تمرین کنید؛ اولین آزمون بازیابی نباید هنگام خرابی Production باشد.

## ۷. به‌روزرسانی امن

1. دسترسی کاربران را موقتاً متوقف کنید.
2. پشتیبان کامل پایگاه داده، رسانه‌ها و تنظیمات بگیرید.
3. نسخه جدید را دریافت کنید؛ `media`، `.env` و پایگاه داده را جایگزین یا حذف نکنید.
4. وابستگی‌ها را نصب/به‌روزرسانی کنید.
5. Migrationها را با دستور دستی و پس از تأیید پشتیبان اجرا کنید.
6. `collectstatic`، `manage.py check` و آزمون‌های پروژه را اجرا کنید.
7. سرویس را راه‌اندازی و سناریوهای پذیرش را اجرا کنید.

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py collectstatic --noinput
.\.venv\Scripts\python.exe manage.py check
```

هیچ‌گاه Migration را در زمان شروع خودکار سرویس اجرا نکنید؛ به‌روزرسانی پایگاه داده باید یک گام کنترل‌شده و قابل‌بازیابی باشد.

## ۸. کنترل‌های پذیرش پیش از تحویل

- [ ] حساب مدیر استانی و حساب‌های کاربران با واحد سازمانی صحیح ایجاد شده‌اند.
- [ ] هر کاربر فقط مراکز مجاز خود را مشاهده می‌کند.
- [ ] پیمانکار فقط مراکز استان/استان‌های قرارداد فعال و معتبر خودش را می‌بیند.
- [ ] قرارداد منقضی یا معلق هیچ دسترسی عملیاتی ایجاد نمی‌کند.
- [ ] ثبت دارایی، ثبت خرابی، تایید کاربر، تایید نهایی IT و بستن درخواست آزمایش شده است.
- [ ] ثبت بازدید، چک‌لیست تجهیزات، تکمیل و تایید بازدید آزمایش شده است.
- [ ] خروجی گزارش و فایل‌های پیوست با نقش‌های مختلف بررسی شده‌اند.
- [ ] پشتیبان تهیه و بازیابی واقعی آن در محیط آزمایشی تأیید شده است.
- [ ] HTTPS، دامنه مجاز، کوکی امن و محدودیت فایروال بررسی شده‌اند.
- [ ] حداقل یک آزمون پذیرش با کاربران واقعی مرکز پایلوت انجام شده است.

**وضعیت تحویل:** تا وقتی HTTPS/شبکه، پشتیبان قابل‌بازیابی و سناریوهای پذیرش در محیط مقصد تأیید نشده‌اند، نسخه را «دموی قابل ارائه» بدانید، نه سامانه عملیاتی آماده بهره‌برداری.
