# راهنمای عملیاتی اصلاحات امنیتی ITAM

این سند مکمل تنظیمات و کنترل‌های پیاده‌سازی‌شده در کد است. **ثبت commit به‌تنهایی به معنی آماده‌بودن محیط Production نیست.**

## مقصدهای Webhook و جلوگیری از SSRF

ارسال رخدادها فقط به URLهای HTTP/HTTPS انجام می‌شود. آدرس‌های loopback، خصوصی، link-local و سایر IPهای غیرعمومی به‌صورت پیش‌فرض رد می‌شوند. مقصدهای خصوصی شبکه سازمان باید با نام میزبان دقیق و از طریق متغیر محیطی زیر مجاز شوند:

```text
ITAM_WEBHOOK_ALLOWED_HOSTS=management.internal.example,his-gateway.internal.example
```

- فقط نام میزبان دقیق وارد شود؛ از wildcard استفاده نکنید.
- DNS در زمان ارسال resolve می‌شود و اتصال به IP اعتبارسنجی‌شده pin می‌شود تا DNS rebinding نتواند مقصد اتصال را عوض کند.
- redirectهای HTTP دنبال نمی‌شوند.
- پورت سفارشی فقط برای میزبان allowlist‌شده مجاز است.
- سرآیندهای رزروشده مانند Host، Authorization و Content-Length از طریق extra_headers قابل بازنویسی نیستند.
- برای مقصد داخلی، DNS باید به IP مورد انتظار resolve شود و فقط hostname موردنیاز در allowlist قرار گیرد.

## فایل‌های رسانه‌ای خصوصی

در Production مسیر `/media/` دیگر مستقیماً با static file server ارائه نمی‌شود. درخواست باید از Django عبور کند تا نشست کاربر و مالکیت رکورد بررسی شود.

- `signatures/`: صاحب امضا یا نقش مجاز در دامنه مرکز.
- `visits/`: دامنه بازدید و مرکز دارایی بررسی می‌شود.
- `hardware/`: مرکز داراییِ اسنپ‌شات بررسی می‌شود.
- `assets/`: مجوز مشاهده دارایی بررسی می‌شود.
- `tickets/`: مجوز مشاهده درخواست خرابی بررسی می‌شود.
- `settings/`: فقط کاربر واردشده می‌تواند نشان سامانه را دریافت کند.
- فایل‌های ناشناخته یا بدون رکورد مالکیت، پاسخ 404 می‌گیرند.

در Nginx/Apache نباید برای پوشه MEDIA یک `alias` یا مسیر مستقیم دانلود تعریف شود که کنترل Django را دور بزند. مسیر `/media/` باید به اپلیکیشن Django proxy شود.

## داده نمونه و حساب مدیر

فرمان `seed_demo` فقط برای توسعه/آزمایش است. اجرای آن اکنون به `--admin-password` صریح نیاز دارد و حساب `admin.province` را به‌صورت superuser ایجاد نمی‌کند.

```powershell
python manage.py seed_demo --admin-password "<unique-development-password>"
```

از گذرواژه نمونه در Production استفاده نکنید و داده نمونه را به محیط عملیاتی وارد نکنید.

## کنترل CI

Workflow با Python 3.11 و 3.12 این مراحل را اجرا می‌کند:

1. نصب وابستگی‌ها
2. `python manage.py check`
3. `python manage.py makemigrations --check --dry-run`
4. `python manage.py test --verbosity 2`

## مواردی که هنوز نیازمند تکمیل/تأیید عملیاتی هستند

- تحویل چندمقصدی Outbox با مدل `OutboxDelivery` و وضعیت/تلاش مستقل برای هر مقصد پیاده‌سازی شده است. رخداد فقط پس از موفقیت همه مقصدهای واجد شرایط sent می‌شود و در retry فقط مقصدهای ناموفق دوباره ارسال می‌شوند. migration شماره `0002_outboxdelivery` باید در زمان انتشار اجرا شود. رخدادهایی که پیش از این migration قبلاً sent شده‌اند به مقصد جدید backfill نمی‌شوند؛ برای ارسال تاریخی باید تصمیم جداگانه گرفته شود.
- صدور، توزیع، چرخش و ابطال اعتبارنامه HWAgent در چرخه واقعی؛ آزمون end-to-end روی رایانه‌های هدف لازم است.
- آزمون عملیاتی PostgreSQL، TLS، reverse proxy، firewall، سرویس پایدار Agent، logging و health checks.
- اجرای واقعی backup و restore و آزمون بازیابی در محیط ایزوله.
- بازبینی داده‌های قدیمی MaintenanceVisit که مرکز ندارند؛ دسترسی آن‌ها عمداً fail-closed است و باید با migration/data-reconciliation جداگانه تعیین تکلیف شوند.
- اجرای تست پذیرش در محیط استقرار و بررسی پیکربندی واقعی storage و وب‌سرور.

هیچ داده‌ای از دیتابیس عملیاتی در این تغییرات پاک یا ویرایش نشده است.
