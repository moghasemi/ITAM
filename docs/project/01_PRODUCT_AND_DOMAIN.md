# محصول و قواعد کسب‌وکار ITAM

## هدف
ITAM چرخه عمر دارایی IT، خرابی و تعمیر، نگهداری قراردادی، کنترل تغییرات سخت‌افزاری، گزارش و یکپارچه‌سازی را در ساختار چندسطحی مدیریت می‌کند.

سه محور اصلی:
1. شناسنامه و چرخه عمر دارایی.
2. قرارداد پیمانکار، بازدید دوره‌ای و SLA.
3. Snapshot سخت‌افزاری و کشف تغییر/برداشت قطعه.

نیازمندی به معنی تکمیل یا پذیرش پیاده‌سازی نیست؛ وضعیت هر workflow باید با مدل، service، view و تست همان branch تطبیق داده شود.

## ساختار سازمانی
کشور → استان → شهرستان → مرکز عملیاتی.

مرکز باید به شهرستان معتبر متصل باشد. مالکیت سازمانی مرکز از جغرافیا جداست و TreatmentManagement برای مالکیت سازمانی به‌کار می‌رود. مدل جغرافیایی نرمال‌شده شهر/محله هنوز کامل نیست و Center.city در مستندات به‌عنوان legacy free text ذکر شده است.

قواعد:
- مرکز خارج از scope نباید دیده شود.
- واحد غیرفعال یا رابطه ناسازگار باید fail-closed شود.
- تغییر parent شهرستان یا استان TreatmentManagement باید invariant مرکزهای وابسته را بررسی کند.
- مرکز واقعی را از روی حدس نسازید.
- منابع عمومی شمار 408 و 413 مرکز را گزارش کرده‌اند؛ فهرست رسمی نام‌به‌نام و provenance برای تعیین عدد معتبر لازم است.

## نقش‌ها
superuser، admin_country، admin_province، admin_county، admin_it، manager، technician و requester.

Role تنها یکی از ورودی‌های تصمیم دسترسی است؛ scope سازمانی، انتساب فعال، وضعیت مرکز/قرارداد، مالکیت رکورد و workflow نیز بررسی می‌شوند. ماتریس کامل را از کد accounts، services و tests استخراج کنید.

## دارایی
شناسنامه تجهیز شامل شناسه اموال، نوع، برند/مدل، سریال، مشخصات، مرکز، محل، امانت‌دار، وضعیت، پیوست و QR است. دارایی با تیکت، بازدید، قرارداد و Snapshot مرتبط است.
- تغییر مرکز/وضعیت نباید دسترسی تاریخی را ناخواسته باز کند.
- دارایی retired نباید از مسیر HWAgent به‌عنوان active پذیرفته شود.
- mutation حساس audit شود.
- فرم و POST هر دو server-side validate شوند.

## تیکت و SLA
گردش مورد انتظار:
reported → acknowledged → arrived → work_started → resolved_declared → user confirmation → IT final confirmation

- reported_at مبدأ SLA.
- زمان پاسخ و رفع از رخدادهای معتبر استخراج شود.
- ساعت کاری، تعطیلات شمسی، اولویت و SLA قرارداد مؤثرند.
- توقف ساعت فقط با علت و بازه مجاز.
- تأیید کاربر و IT نهایی مستقل‌اند.
- پیمانکار نباید تأیید نهایی IT یا کاربر را دور بزند.
- تغییر مستقیم status در Admin نباید مسیر عادی باشد.

## پیمانکار و قرارداد
- دسترسی پیمانکار به مرکز از انتساب فعال و تاریخ‌دار همان مرکز و قرارداد معتبر مشتق شود.
- قرارداد استانی به‌تنهایی انتساب صریح مرکز ایجاد نمی‌کند.
- جدول legacy Contract.centers مرجع مجوز نیست.
- قرارداد استانی چندمرکزی باید scope هر عملیات را به مراکز منتسب محدود کند.
- قرارداد غیر استانی طبق منطق مستند فعلی باید دقیقاً یک مرکز مرتبط داشته باشد؛ پیش از تغییر، کد و تست را بخوانید.

## Snapshot سخت‌افزاری
baseline پس از workflow تأیید دو نفره قفل می‌شود. snapshotهای بعدی missing/changed/added و تغییر مشخصات را ثبت می‌کنند. سریال قدیم/جدید و شواهد باید حفظ شوند. Admin و API نباید قفل را دور بزنند.

## تعمیر مستقل و درخواست عمومی
نیازمندی شامل برآورد، تصمیم استان، نتیجه تعمیر، ارزیابی، اختلاف هزینه و ارجاع است. تصمیم مدیر، تخصیص کارشناس و وضعیت اجرایی باید مستقل بمانند. stale و duplicate submission رد و ممیزی شوند.

## گزارش و export
گزارش‌های SLA، عملکرد پیمانکار، موجودی، compliance بازدید، failure analysis، Snapshot changes و درخواست/ارجاع. فیلتر و export باید scope صفحه را رعایت کنند و CSV/XLSX در برابر formula injection محافظت شوند.

## مرز MVP
برای موارد خارج از مرحله جاری به سند زمینه 1.2 و backlog نسخه 1.3 رجوع کنید. هاست/Production، نرمال‌سازی کامل جغرافیا و frontend مستقل در اولویت فعلی نیستند.
