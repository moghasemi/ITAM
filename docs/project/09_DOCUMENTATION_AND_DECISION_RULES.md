# قواعد مستندسازی و تصمیم‌ها

## اصل
نیازمندی، کد موجود، CI و پذیرش دستی را با هم مخلوط نکنید.

## وضعیت قابلیت
- Implemented: در commit مشخص وجود دارد.
- CI verified: تست خودکار روی commit مشخص موفق.
- Locally verified: اجرای واقعی محلی با شواهد.
- Accepted: سناریوی پذیرش با نقش/داده مناسب تأیید شده.
- Planned: نیازمندی یا تصمیم آینده.
- Open: نیازمند بررسی.
- Deferred: خارج از مرحله جاری.

## قالب تصمیم معماری
- شناسه و تاریخ.
- عنوان و وضعیت proposed/accepted/superseded.
- زمینه و مسئله.
- گزینه‌ها.
- تصمیم و پیامدها/trade-offs.
- دامنه کد/DB.
- تست لازم.
- PR/commit مرجع.
- تصمیم‌گیرنده.

## به‌روزرسانی
هر PR که محصول، امنیت، معماری، workflow، داده یا عملیات را تغییر دهد باید سند مربوط را به‌روز کند. تغییر UI، UI docs و manual QA را به‌روز کند؛ تغییر schema، migration/data safety docs را به‌روز کند.

## تعارض اسناد
تاریخ سند به‌تنهایی برتری ندارد؛ commit و منبع را بررسی کنید. README ممکن است نیازمندی را توصیف کند نه پیاده‌سازی کامل. سند معماری ممکن است target architecture باشد. اختلاف را حذف یا اصلاح بی‌صدا نکنید؛ Gap ثبت کنید.

## سبک
فارسی روشن؛ نام model/field/class/command/path عیناً در code span. ادعای قطعی بدون شواهد نکنید. command خطرناک را به‌عنوان دستور copy/paste توصیه نکنید. secret و داده شخصی در مثال نباشد. CI و local جدا گزارش شوند.

## نسخه‌بندی
سند جامع نسخه‌دار است. نسخه جدید باید نسخه قبلی را حفظ کند، تاریخ و commit basis داشته باشد، تغییر وضعیت و تصمیم‌ها را ثبت کند و backlog را بازبینی کند.


## قانون اجرایی: مستندسازی هم‌زمان و بدون درخواست اجازه
از تاریخ 2026-11-18، به‌روزرسانی اسناد بخشی از Definition of Done هر کار است و برای اصلاح مستندات مرتبط نیازی به اجازه جداگانه کاربر نیست.

- پس از هر تصمیم: تصمیم، زمینه، گزینه‌های بررسی‌شده، دلیل، پیامد، وضعیت و تاریخ در Decision Log ثبت شود.
- پس از هر تغییر فنی: سند دامنه‌ای مرتبط، معماری/امنیت در صورت اثر، و سند جامع پروژه در صورت تغییر وضعیت مهم به‌روز شود.
- پس از هر تست: commit/branch، محیط، فرمان یا سناریو، نتیجه و محدودیت‌ها ثبت شود؛ CI و تست محلی هرگز با هم اشتباه نشوند.
- پس از هر مرحله: وضعیت PR/CI، backlog، ریسک‌ها و اقدام بعدی به‌روز شود.
- تغییر مستندات مرتبط می‌تواند بدون تأیید موردی در شاخه کاری مناسب commit شود؛ تغییر مستندات نباید بهانه‌ای برای Merge یا انتشار باشد.
- اگر تغییر هنوز قطعی نیست، آن را Proposed/Open ثبت کنید؛ تصمیم موقت را به‌عنوان Accepted ننویسید.
- اسناد قبلی و نسخه‌های منتشرشده حفظ شوند؛ تاریخچه با نسخه‌بندی و Decision Log روشن بماند.

این قانون مجوز Merge، Deploy، Migration، Seed، حذف/بازنویسی داده، یا عملیات مخرب نیست. این موارد همچنان نیازمند اجازه صریح جداگانه‌اند.
