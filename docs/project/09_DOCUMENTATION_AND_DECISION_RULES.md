# قواعد مستندسازی و تصمیم‌ها

## اصل
نیازمندی، کد موجود، CI و پذیرش دستی را با هم مخلوط نکنید.

## وضعیت قابلیت
- Implemented: در commit مشخص وجود دارد.
- CI verified: تست خودکار روی commit مشخص موفق.
- Locally verified: اجرای واقعی محلی با شواهد.
- Accepted: سناریوی پذیرش با نقش/داده مناسب تأیید شده.
- Planned: نیازمندی یا تصمیم آینده.
- Open: نیازمند بررسی.
- Deferred: خارج از مرحله جاری.

## قالب تصمیم معماری
- شناسه و تاریخ.
- عنوان و وضعیت proposed/accepted/superseded.
- زمینه و مسئله.
- گزینه‌ها.
- تصمیم و پیامدها/trade-offs.
- دامنه کد/DB.
- تست لازم.
- PR/commit مرجع.
- تصمیم‌گیرنده.

## به‌روزرسانی
هر PR که محصول، امنیت، معماری، workflow، داده یا عملیات را تغییر دهد باید سند مربوط را به‌روز کند. تغییر UI، UI docs و manual QA را به‌روز کند؛ تغییر schema، migration/data safety docs را به‌روز کند.

## تعارض اسناد
تاریخ سند به‌تنهایی برتری ندارد؛ commit و منبع را بررسی کنید. README ممکن است نیازمندی را توصیف کند نه پیاده‌سازی کامل. سند معماری ممکن است target architecture باشد. اختلاف را حذف یا اصلاح بی‌صدا نکنید؛ Gap ثبت کنید.

## سبک
فارسی روشن؛ نام model/field/class/command/path عیناً در code span. ادعای قطعی بدون شواهد نکنید. command خطرناک را به‌عنوان دستور copy/paste توصیه نکنید. secret و داده شخصی در مثال نباشد. CI و local جدا گزارش شوند.

## نسخه‌بندی
سند جامع نسخه‌دار است. نسخه جدید باید نسخه قبلی را حفظ کند، تاریخ و commit basis داشته باشد، تغییر وضعیت و تصمیم‌ها را ثبت کند و backlog را بازبینی کند.
